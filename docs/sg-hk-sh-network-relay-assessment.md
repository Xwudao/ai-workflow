# 新加坡—香港—上海中转链路评估（2026-09-26）

## 拓扑与结论

候选路径：`txsp2`（新加坡，43.160.224.101）→ `txhk`（香港，43.161.227.45）→ `gate`（上海，110.40.167.56）；对照路径为 `txsp2` → `gate` 直连。以上 IP 为测试时的公网出口地址，使用前需再次核实。当前**没有部署 WireGuard，也没有修改服务器配置或路由**。

本次采样中经香港的两段链路合计约 65.8 ms，直连约 106.3 ms，预计可节约约 40 ms RTT（约 38%）。两段链路各自 20 次 ping、100 轮 ICMP MTR 及 100 次 TCP 建连均未发现终点丢包/建连失败；直连 ICMP 丢包约 29–35%，TCP 建连亦出现失败和重传迹象。建议将香港作为候选中转，但实际 WireGuard UDP 效果、长时间稳定性和吞吐量仍需部署前/后进一步验证。

命令示例：在源机器执行 `ping -q -c 20 -W 2 <目标公网IP>` 和 `mtr -n -rw -c 100 <目标公网IP>`；TCP 补测采用实际 SSH 监听端口的 `mtr -n -T -P <端口> -rw -c 100 <目标IP>`，再用 Python `socket.create_connection(timeout=2)` 每次间隔 0.3 秒顺序建连 100 次。22 端口在目标机不开放，不能用它测试真实 SSH 服务。

注意：TCP MTR 输出存在异常秒级中间跳及终点采样不足，不能据其推断实际 TCP 丢包率；用顺序 TCP 建连结果交叉验证。TCP 建连失败率不等同于线路丢包率，成功建连耗时也受 TCP 重传影响。中间路由器 ICMP 不回应/限速不能直接视为转发丢包。MTR 单程探测、ping RTT 与两段 RTT 相加均不能保证真实隧道表现。

## 后续验证与回滚

如未来实施双段 WireGuard，应先备份受影响配置，在临时路径验证 UDP 可达、实际隧道端到端 RTT、连续丢包、吞吐和双向路由，然后再决定是否切流。目标端到端 RTT 粗估约 66–75 ms（两段合计 65.8 ms 加隧道处理开销），比本次直连约 106 ms 低约 30–40 ms；这不是实测承诺。若切流后质量不达标，应撤销新加的策略路由/转发及隧道配置，恢复此前备份并回到 SG→SH 直连。本次仅测试，**无需回滚**。
